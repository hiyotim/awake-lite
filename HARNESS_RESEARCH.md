# Coding-agent activity support in AwakeLite

Research date: 2026-10-31.

This survey predates the narrowed seven-family scope. It records source findings and earlier design options, including products outside the current plan. [SPEC.md](SPEC.md) owns current scope; [ARCHITECTURE.md](ARCHITECTURE.md) owns the proposed design. The process-watching fallback, broader rollout order, and storage alternatives discussed here are historical proposals, not current implementation instructions.

Recommendation from the survey: retain a native app and add a shared state receiver with small adapters for agent hooks and APIs. Broad coverage can fit a lightweight app. Do not promise accurate observation of any arbitrary harness without connecting to it.

This is documentation and source research, not integration acceptance. An available event means an adapter may be feasible. AwakeLite does not yet implement these integrations. No agent configuration was changed during the research. Sources and installed-version observations below are dated findings, not freshly reverified claims.

## Existing app and local observations

At the time of the survey, AwakeLite contained 176 Swift lines across four files. AwakeController checked for opencode, omp, and codex every five seconds. ProcessScanner invoked pgrep. Process presence alone determined the sleep hold. The IOKit mechanism could be retained.

Local inspection found OpenCode 2.2.5, OMP 18.14.0, standalone Codex CLI 0.160.0, and the desktop app's Codex package 0.166.0-alpha.5.1. User-level Codex configuration enabled hooks. A schema generated by the installed Codex contained hook events and active, idle, notLoaded, and systemError states, plus waitingOnApproval and waitingOnUserInput flags. Schema generation does not prove delivery from desktop chats.

Installed OpenCode and OMP observers provide local examples of state handling. Their code does not prove compatibility with AwakeLite. Research did not require changing or enabling them.

## Shared protocols and existing implementations

ACP describes the complete session/prompt cycle, responses, cancellation, and permissions. It is usable when the app participates in the client-agent connection. The inspected docs did not establish a universal passive subscription to every independently launched CLI and IDE. A proxy or custom launcher adds scope and changes how agents are started. [Prompt turn](https://agentclientprotocol.com/protocol/v1/prompt-turn)

Sessionpipe normalizes lifecycle events. Protocol v1 includes turn.started, turn.ended, attention.needed, attention.cleared, and background-work metadata. The specification is Draft. The site and inspected source catalog confirm adapters for Claude Code, Codex, Gemini CLI, Antigravity, and Devin. Cursor, Copilot CLI, Droid, Kiro, and OpenCode are listed as upcoming integrations, not completed coverage. Its hook configuration launches a Node client. It is a useful reference for formats and fixtures, but a mandatory dependency would conflict with keeping the app's native runtime. Protocol compatibility could be considered later. [Protocol](https://sessionpipe.org/protocol/), [Adapters](https://sessionpipe.org/protocol/adapters/), [current source](https://github.com/spacesheep-dev/sessionpipe/tree/main/packages/core/src/adapters)

Caffeine already uses a Swift menu-bar app, bundled CLI, and optional agent hooks. The author separates process watching from turn observation. Its inspected AgentLifecycleStore atomically writes separate session files. This demonstrates the practicality of that structure, not reliability for all our scenarios. In particular, file age does not prove task completion. [Overview](https://github.com/iannuttall/caffeine#agent-watch-follows-active-turns), [store](https://github.com/iannuttall/caffeine/blob/main/Sources/CaffeineCore/AgentLifecycleStore.swift)

An MCP tool that the model must choose to call at work start and completion is unsuitable as the primary source of truth. Calls depend on model behavior and do not cover crashes. CPU usage, network activity, and transcript parsing are also poor primary activity signals.

## Structure proposed during research

Retain one .app with a menu-bar app and a small native CLI helper. Hooks invoke the helper. Pi, OMP, and other plugin-based harnesses use their existing runtime to report the same states. AwakeLite need not ship an extra Node or Python runtime.

Adapters report only what sleep control needs:

- Source and agent instance.
- Session and work identifiers.
- Working, waiting, idle, or unknown state.
- Update order and metadata for verifying the owner's lifecycle.

Prompts, responses, tool arguments, credentials, and transcript contents are unnecessary. Raw hook input can contain such data, so the helper must extract an allowlist of fields without storing the original payload.

An initial option was a private user directory with atomic state files separated by instance and session. Native macOS file observation and a startup scan recover persisted state. Separate files reduce competition between independent agents. A watcher does not establish completeness or protect against late updates. A small restart and concurrency prototype should test the storage decision. The later architecture document selects independent event files with app-owned checkpoints rather than treating these early state-file ideas as final.

Hold the assertion while at least one task is confirmed working. Waiting for a model response, command completion, or child work counts as work. Human waits allow release only when no other work remains. A short release delay may bridge known automatic continuations.

Show unknown separately. Lack of new tool events does not mean idle. A heartbeat proves observer liveness, not task completion. A process can survive a lost Stop event. Use snapshot APIs for recovery where available, and document limitations elsewhere.

Do not use one global start/stop counter without work IDs. Duplicates, late events, and concurrent sessions break it. Pair PID checks with instance identity so PID reuse cannot revive an old record.

## Keeping the app small

The core owns session state and one IOKit assertion. Adapters own harness differences. Many additional brands need hook configuration and a few normalized fields. Plugin APIs require a small plugin; some IDEs may need a bridge extension.

The menu needs aggregate status, pause, launch at login, quit, and an integration window. The window handles product discovery, connection, disconnection, and compatibility status. Product discovery is not evidence that an integration is connected or verified.

The installer preserves existing hooks, adds only its owned entries, and removes only those entries. Respect Codex hook trust and other products' workspace trust. Connecting must not alter agent responses, permission decisions, or unrelated hooks.

An early option retained process watching as an explicitly selected compatibility fallback. Silently substituting it for event observation would restore the battery problem of idle open agents. The later specification does not include this fallback in automatic activity policy.

An event-based design can reduce background process polling. This is an expected design property, not a measured improvement. CPU, wakeup, and battery measurements have not been performed for it. If disabled adapters do not run, broader coverage mainly increases configuration and verification work.

## Initial rollout proposal and validation boundaries

The earlier broad rollout proposal started with Codex, OpenCode, and OMP, then Claude Code, Gemini CLI, and Cursor, followed by other families. This proposal predates the narrowed scope and is superseded by ROADMAP. Do not implement the extra products listed here merely because they appear in the survey.

For each adapter, verify:

- An open idle agent.
- Request start, a slow model response, and a long command.
- A question for the user and a permission prompt.
- Successful completion, failure, cancellation, and automatic continuation.
- Parallel sessions and working subagents.
- Agent crash, AwakeLite restart, and lost events.
- Hook installation and removal with unrelated settings present.

Record product version, CLI, desktop, IDE, remote, and cloud compatibility separately. Hooks running on another machine do not automatically reach the Mac's local directory; that needs a separate transport. Fully cloud-hosted work does not itself require keeping the local Mac awake when it has no local dependency.

The initial engineering estimate was several working days for the core and first adapters. Broader verified coverage was estimated at one to two working weeks, or longer for desktop incompatibilities. This is an effort estimate, not a confirmed schedule. IDE bridges and incomplete lifecycle sources need separate estimates.

The app can remain a small native menu-bar tool. Broad coverage's recurring cost is maintaining and verifying agent contracts and versions, not necessarily running more persistent AwakeLite services.
